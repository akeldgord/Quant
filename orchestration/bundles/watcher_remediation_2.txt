B. What was built

Per orchestrator instruction argus-watcher-remediation-002 (pushed via
GitHub, commit e0d3504), the prior watcher remediation
(orchestration/checkpoints/watcher_remediation.md, commit a700ee1) was
rejected as insufficient for unattended phase advancement. This task
substantially rewrote scripts/argus_orchestrator_watch.py and
tests/unit/test_orchestrator_watch.py to close all 8 numbered requirement
categories in the instruction. Full reasoning and per-category detail is
recorded in docs/DECISION_LOG.md, entry "Watcher remediation round 2:
orchestrator-requested hardening (argus-watcher-remediation-002)". Summary:

1. Durable, fail-closed state handling. read_state_safe() distinguishes
   OK/MISSING/INVALID outcomes. A malformed/corrupt/schema-invalid state
   file fails closed (STATE_INVALID) without being rewritten (preserved for
   forensic inspection). A missing state file with an ACTIVE instruction
   outstanding is not assumed to be a first execution: the watcher
   cross-checks orchestration/AGENT_HANDOFF.md and either recognizes the
   instruction as already completed (STATE_REBUILT_FROM_HANDOFF, no
   relaunch) or fails closed (STATE_MISSING_FAIL_CLOSED, requires a new
   INSTRUCTION_ID). State writes now fsync the file and its parent
   directory.

2. A failed Claude process now always fails the run. This was the literal
   bug the orchestrator identified: the prior tick() recorded exit_code but
   never branched on it before calling verify_handoff() -- a nonzero exit,
   timeout, or launch-time OSError (e.g. FileNotFoundError) could still be
   accepted as COMPLETED if handoff/evidence files happened to look valid.
   tick() now fails the run immediately on any non-zero/None exit code,
   before any other verification runs, logging a diagnostic bounded to a
   few hundred characters.

3. Evidence must be new, immutable, and structurally valid.
   CHECKPOINT_PATH/BUNDLE_PATH are normalized and validated
   (repository-relative, correct directory/extension, no
   traversal/absolute/symlink paths), must not have existed at the
   pre-launch HEAD, and must show as newly ADDED (not modified) in the
   run's commit range. Content is structurally validated -- a one-line
   placeholder now fails. AGENT_HANDOFF.md is validated against the full
   11-field schema from orchestration/PROTOCOL.md section 5 (previously
   only 4 of 11 fields were checked), rejecting duplicates, missing fields,
   and a reused HANDOFF_ID. CURRENT_COMMIT and the checkpoint's own
   GIT_COMMIT must resolve to a commit created during the run.

4. Branch-movement and commit-attribution detection. Local and remote HEAD
   are compared immediately before launch. Post-run HEAD must descend
   linearly from pre-launch HEAD -- rewritten/force-pushed history or a
   merge commit anywhere in the run's range fails the run. Every commit in
   range must carry the exact trailer "ARGUS-INSTRUCTION-ID:
   <instruction_id>"; a substring-matching or differently worded trailer
   does not count.

5. Mechanical self-authorization prevention. The blob hash of
   orchestration/ORCHESTRATOR_INSTRUCTIONS.md is captured immediately
   before launch and re-checked (via git hash-object against the live
   working-tree file, catching an uncommitted edit too) after Claude
   exits. Any difference fails the run outright, even if later committed
   and pushed by the implementation agent itself.

6. Explicit, sequence-based phase gating with Phase 1.5 support.
   PHASE_SEQUENCE is now an explicit ordered tuple of string tokens ("0",
   "1", "1.5", "2", ..., "6", "6.5", ..., "11"), compared only by list
   position, never as floats. A new APPROVES_PHASE instruction field
   distinguishes same-phase remediation (APPROVES_PHASE: NONE, requires
   AUTHORIZED_PHASE == current_phase) from phase advancement
   (APPROVES_PHASE == current_phase == last_completed_phase,
   awaiting_orchestrator_review == true, AUTHORIZED_PHASE must be the
   immediate successor -- no skipping a phase or sub-phase).

7. Strict instruction-field parsing. Duplicate fields, missing fields, an
   unknown STATUS, a malformed ISSUED_AT timestamp, a non-full-SHA
   TARGET_COMMIT, an empty/NONE AUTHORIZED_ACTION, and an invalid
   AUTHORIZED_PHASE/APPROVES_PHASE are all rejected for an ACTIVE
   instruction. The NO_INSTRUCTION placeholder keeps a deliberately
   lenient, explicitly-validated safe schema.

8. Conservative, ordered post-run verification: process-exit success, then
   ancestry/attribution, then instructions-file integrity, then
   handoff/evidence completeness, then clean-worktree/pushed-HEAD equality
   -- matching the order specified by the instruction.

Also added: a defensive try/except around each tick() call inside
run_forever() so one bad tick cannot crash the whole watcher process
(--once runs intentionally still let an exception propagate, since an
operator is watching interactively).

orchestration/PROTOCOL.md sections 4, 5, and 7 and docs/OPERATIONS.md were
updated to describe the above as mechanically-enforced requirements, not
just implementation detail.

M. Known bugs / debt
- Known limitation on self-authorization prevention (section 5): this
  protocol is file-trust-based, not cryptographically signed. The
  blob-hash-unchanged check reliably catches an implementation agent that
  edits the live instructions file (committed or not), and the
  target-commit diff-scope check independently catches a self-authored
  instruction whose TARGET_COMMIT points at the pre-launch HEAD while other
  files also changed in the same range (the realistic case, and the one
  test_self_authored_instruction_cannot_launch exercises). A maximally
  adversarial run that points a self-authored instruction's TARGET_COMMIT
  at its own freshly-created HEAD is not fully excluded by these mechanisms
  alone -- closing that completely would require a cryptographic signing
  step outside this protocol's current file-trust design. Stated here
  explicitly per CORE-011 ("truth outranks impressive P&L") rather than
  overclaiming complete prevention.
- The watcher's real (non-mocked) Claude CLI invocation itself
  (`claude -p <prompt>`) still has not been exercised against a real
  `claude` process in this sandbox -- unchanged limitation from prior
  rounds; every test and the real `--once` runs here either mock it or
  never reach the launch step.
- validate_checkpoint_content()/validate_bundle_content() are deliberately
  simple substring/marker-based structural checks (not a full grammar) --
  sufficient to reject a placeholder or wildly malformed document, but not
  a rigorous document schema. If a future instruction wants stricter
  validation, that's a protocol-contract question for the orchestrator.
